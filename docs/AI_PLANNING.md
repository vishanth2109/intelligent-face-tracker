# AI Planning & Development Process

## 1. Project Overview

The project is an **Intelligent Face Tracker with Auto-Registration and Visitor Counting**.

The objective is to process a video stream, detect and track faces, recognize previously registered visitors, automatically register new visitors, and record accurate ENTRY and EXIT events.

The system was developed using an AI-assisted development approach. AI was used primarily for architecture planning, code generation, debugging assistance, test creation, documentation, and explaining implementation decisions.

All generated code was reviewed, tested, modified, and validated during development.

## 3. Architecture Planning

The initial architecture was designed around separate components with clearly defined responsibilities.

### Main Components

* `main.py` — application pipeline and video processing loop
* `config.py` — configuration loading
* `detector.py` — detection-related functionality
* `tracker.py` — YOLO + ByteTrack tracking
* `recognizer.py` — InsightFace recognition and embedding handling
* `visitor_manager.py` — visitor identity and ENTRY/EXIT management
* `database.py` — SQLite persistence
* `event_logger.py` — structured application event logging
* `utils.py` — utility functions

The main processing pipeline was designed as:

```text
Video Source
     |
     v
YOLO Face Detection
     |
     v
ByteTrack Tracking
     |
     v
InsightFace Recognition
     |
     v
Visitor Manager
     |
     +------ Known Face ------> Existing FACE_ID
     |
     +------ Unknown Face ----> Auto Registration
     |
     v
ENTRY / EXIT Management
     |
     +------ SQLite Database
     |
     +------ Event Log
     |
     +------ Cropped Face Images
     |
     v
Annotated Output
```

## 6. Identity Design

One of the important architectural decisions was to use two different identifiers.

### TRACK_ID

`TRACK_ID` is generated by the tracking system.

It represents a temporary tracked object within the video stream.

Example:

```text
TRACK_ID = 7
```

A tracker ID can change when the same person disappears and later reappears.

### FACE_ID

`FACE_ID` represents the persistent identity stored in the database.

Example:

```text
FACE_0001
FACE_0002
FACE_0003
```

This separation allows the system to recognize the same person even when a new tracking ID is assigned.

---

## 7. Face Recognition Strategy

InsightFace is used to generate face embeddings.

The embeddings are normalized before similarity comparison.

The system compares a newly observed embedding with stored visitor embeddings.

The configured recognition threshold is:

```text
similarity_threshold = 0.45
```

If a sufficiently similar stored embedding is found, the visitor is treated as an existing person.

Otherwise, the system proceeds toward automatic registration.

---

## 8. Automatic Face Registration

To reduce the possibility of registering a temporary or poor-quality detection immediately, the system does not register an unknown face from a single recognition attempt.

A new face is evaluated across multiple attempts.

Current registration logic:

```text
Attempt 1
   |
Attempt 2
   |
Attempt 3
   |
   v
Average Embedding
   |
   v
Register New FACE_ID
```

The current implementation requires three recognition attempts before registering an unknown visitor.

The embeddings collected during these attempts are averaged and normalized before being stored.

---

## 9. ENTRY Event Design

An ENTRY event is created when a tracked face is successfully assigned to a persistent `FACE_ID`.

The event contains information including:

* FACE_ID
* TRACK_ID
* event type
* timestamp
* cropped image path
* confidence

The system prevents repeated ENTRY events for the same active tracking session.

Therefore, multiple video frames containing the same person do not create multiple ENTRY records.

---

## 10. EXIT Event Design

A visitor remains an active track while the tracker continues to detect the person.

When the track is no longer detected, the system maintains a missing-frame counter.

The configured value is:

```text
max_missing_frames = 50
```

If the visitor remains missing for the configured number of frames, the active tracking session is closed.

The system then:

1. determines the visitor's `FACE_ID`
2. records the EXIT timestamp
3. saves the latest available face crop
4. inserts an EXIT event into SQLite
5. closes the tracking session
6. removes the active track from memory

This design prevents an EXIT event from being generated immediately because of a single missed detection.

---

## 11. Unique Visitor Counting

Unique visitor counting is based on persistent `FACE_ID` values rather than raw tracker IDs.

For example:

```text
TRACK_ID 1 -> FACE_0001
TRACK_ID 8 -> FACE_0001
TRACK_ID 14 -> FACE_0001
```

These are treated as the same visitor because they map to the same persistent identity.

This prevents re-identification from incorrectly increasing the unique visitor count.

The SQLite `persons` table provides persistent visitor records across application runs.

---

## 12. Database Design

SQLite was selected because it is lightweight, local, and suitable for the hackathon's single-application deployment model.

The database currently contains three primary tables.

### `persons`

Stores persistent visitor identities.

Important fields include:

```text
id
face_id
first_seen
last_seen
embedding
created_at
```

### `events`

Stores visitor ENTRY and EXIT events.

Important fields include:

```text
id
face_id
track_id
event_type
timestamp
image_path
confidence
```

### `tracks`

Stores tracking sessions.

Important fields include:

```text
id
face_id
track_id
start_time
end_time
status
```

## 13. Event Logging

In addition to SQLite, the application maintains:

```text
logs/events.log
```

The log records important application events such as:

* face recognition
* new face registration
* ENTRY
* tracking activity
* EXIT
* embedding-related processing

This provides a human-readable audit trail in addition to structured database storage.

---

## 14. Image Logging

The system saves cropped face images for visitor events.

The intended structure is:

```text
logs/
├── entries/
└── exits/
```

Each saved image includes identifying information in its filename, together with a timestamp.

These images provide visual evidence for recorded ENTRY and EXIT events.

## 15. Configuration-Driven Development

Important parameters were moved into:

```text
config.json
```

Examples include:

```json
"confidence": 0.5,
"image_size": 1280,
"frame_skip": 3,
"similarity_threshold": 0.45,
"embedding_update_interval": 30,
"max_missing_frames": 50,
"device": "cpu"
```

This makes the system easier to tune without modifying Python source code.

## 16. RTSP Support

The application was designed to support both:

```text
Video File
```

and

```text
RTSP Camera Stream
```

The source type is selected through configuration.

Example:

```json
"camera": {
    "type": "rtsp",
    "rtsp_url": "rtsp://YOUR_CAMERA_URL"
}
```

The same tracking and recognition pipeline can therefore be used for either a development video or a live camera source.

## 19. Performance Optimization

Performance was considered after the functional pipeline was working.

The main optimization used in the application is configurable frame skipping.

Current configuration:

```json
"frame_skip": 3
```

This reduces how frequently the expensive detection and recognition pipeline needs to run.

Tracking information from the previous processed frame can continue to be displayed between processing cycles.

Performance measurement was also added during development to observe recognition processing frequency.

The optimization was tested against the working pipeline rather than applied before functionality was validated.
